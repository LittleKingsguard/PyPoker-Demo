# PyPoker-Demo — L1 end-to-end battery

- **Layer:** L1 · **Unit:** phase1 · **Rev:** 11 · **Date:** 2026-11-10
- **Covers:** what `tests/e2e/` must drive, what "green" means before code exists (D-11), the catalogue cases D-19, D-20 and D-21 add, the two families the second game shape and the sized action add (D-29), and the family D-33's seat count and widened history add (D-33)
- **Ceiling:** 100 lines. At the ceiling, split by owner — never append

## 1. What green means here

The examiner validates the battery before the code (D-11, `strata/examiner.md` §1). Every assertion below is red against absent code, which is the expected state of a design-stage battery: "red" is not the finding, and "completable" is (`strata/examiner.md` §3). This layer is green when the battery drives only declared surfaces, asserts observable outcomes, is satisfiable by some implementation, and covers the families of §3.

## 2. Rules the battery is written under

- It calls only the entry points of `e2e-surface.md` §3, through the `harness` module where support is needed, and reaches past no entry point (brief §5). The shapes it reads are `records.md`'s **required** keys and nothing beyond them (D-13).
- It asserts outcomes, never an internal call, an internal shape, or a restatement of an implementation (`strata/examiner.md` §2).
- It is network-free, CPU-only, self-sufficient and run from the repository root with the project venv. A case that needs a checkpoint or a pool builds one with a minimal budget; reading `training.checkpoints()` as an index is not a dependency on a shipped artefact, but asserting retention is done against a run the case builds itself (D-8, ASM-18).
- It imports nothing beyond the standard library and the declared entry points — `unittest` included, and no third-party package — so it adds no dependency to the audience's environment and runs under either runner (C-C5, D-8). The project venv does carry `pytest` 9.2.0 (the `dev` extra of `pyproject.toml`, not a battery dependency), and that is how the batteries are executed.
- **How the batteries are run.** One battery per invocation, from the repository root: `.venv/bin/python -m pytest tests/e2e -q` for this one, `.venv/bin/python -m pytest tests/<module> -q` for a module's, and `scripts/run-all-tests.sh` for all thirteen, which is what "run the tests" means. A bare `pytest tests` cannot collect this tree: sibling batteries reuse file basenames — `test_errors.py` in two, `test_seeds.py` in two, `test_episode.py` in two, `test_guardrails.py` in two — and each battery imports its own same-directory support module (`_evaluation_support.py`, `_join_support.py` and their kin), so the prepend import mode aborts with an import file mismatch while the importlib mode breaks those helper imports. Measured 2026-11-05: `.venv/bin/python -m pytest tests --collect-only -q` reports five such errors, one per duplicated basename (`scripts/run-all-tests.sh`, D-11). The same battery is also collectable by `unittest` — `.venv/bin/python -m unittest discover -s tests/e2e -t .`, the census `docs/L3/evaluation/guardrails.md` G22 runs — which is why the write-root bullet below covers both runners rather than the pytest one alone.
- **Where a battery writes.** Nowhere under the repository's `checkpoints/`, **whichever runner runs it.** Each documented runner loads a hook that establishes the session's write root before a case runs: `tests/conftest.py` under `pytest`, for every one of the thirteen batteries, and `tests/e2e/__init__.py` under the `unittest` census, whose `-t .` form imports that package before any case module — `unittest` loads no conftest at all. Each hook points `PYPOKER_CHECKPOINT_ROOT` — the one ambient override `training.layout` reads on every call — at a private `tempfile.mkdtemp(prefix="pypoker-battery-checkpoints-")` outside the repository and removes it at exit, so a battery that trains creates `seed-4103`, `R2/` or `R4/` in a temporary tree and the reader's shipped set is untouched. The `-t .` in that census command is not decoration: only that form imports this battery as the package `tests.e2e`, so only that form loads the hook — discovery without it imports no package init, which is why it collects a fraction of the cases rather than every one of them and still writes the shipped tree, and why `tests/e2e/README.md` and `docs/L3/evaluation/guardrails.md` G22 spell the command with it. The establishment is **unconditional** — an inherited value, `<repo>/checkpoints` included, is replaced, so a developer's shell cannot redirect a battery into the shipped tree — and **idempotent across the two hooks**: the hook that makes the root records it in a marker no file under `src/` reads, and the second hook declines, so a process that loads both ends with one root and `PYPOKER_CHECKPOINT_ROOT` stays the only name that points a run. The mechanism is why both runners are covered rather than the `pytest` one: a census that loads no hook passes every case and still writes the shipped tree, because the `pytest` hook is not loaded by `unittest` (`docs/L3/harness/layout.md` §5, `docs/L2/training/write-root.md` §4, `docs/L3/training/checkpoints.md` §5, D-8, ASM-18). A run a reader starts deliberately still writes the shipped layout; that is intended and `getting-started.md` §4 warns of it.
- No case is skipped or conditionally disabled. A case that cannot run is a finding against the test writer (D-11).
- League cases assert cell counts from K arithmetically, and where a table is actually played the case uses the smallest legal membership — the three baselines and one variant, K = 4, six cells — because `evaluation.matrix` takes a table budget rather than a hand count and the live cell is fixed at 120 hands (ASM-14). The battery proves the scheduler's arithmetic; the shipped table proves the cost.
- A timing case asserts that a cost record exists and carries hands and seconds per hand; it never asserts that a wall clock was beaten, which would be a flaky test and not a contract (ASM-15).
- Each case carries an id of the form `FAM-<n>.<k>`; the layer return cites them.

## 4. The blind instances

`e2e-surface.md` §5 marks 37 rows `general`. For each, the battery carries at least one case whose subject is that row and whose instance — the seed, the configuration, the membership, the cell size, the hand count, the checkpoint, the case — appears in no design document (D-15). The test writer invents them from the declared surface; the L1 documents show no instance for a `general` row, which is what keeps the walkthrough blind (D-14, D-15).

The **thirteen** `fixed` rows are exempt: their one instance is the project's own — the two game shapes of D-2 and D-29, the two encodings of D-3, the baselines of D-6, the rungs of brief §2, the league of D-16 and the two rules of D-19. `features.observation_spec` is one of them because an encoder exists only by a declared encoding, and `engine.game_shapes` is one because its instances are the declaration itself, so no invented instance of either can be built through the surface (`e2e-surface.md` §5, `shapes.md` §2).

## 5. What the battery does not cover

Module-internal behaviour belongs to `tests/<module>/`, and the harness line ceiling belongs to `strata-lint` with the counts of `modules.json` (brief §5). The battery judges the map's joins — the invariants a single module cannot check about itself (D-3, D-16): that the pool the loop samples is the pool the table measures, that both arms of a pair held one pool, and that a table's rows are comparable because its cells were played at one hand count (D-16, ASM-16).

It also does not assert a table's *values*: no case requires a member to outrank a baseline, because that is what the run measures and not what the surface promises (D-6, D-16). Nor does it assert that a rule trains *better*: the catalogue's two rules are asserted to be one contract and two arithmetics, and which of them escapes a raise habit is a measurement recorded in a record, never a case (D-19, `rules.md` §2–§3). Nor that a utility plays *better*: the two utilities are asserted to be one contract, one capacity and two rewards, the changed reward is observed through the two arms' curves and through every record that must name it, and whether a risk-averse objective lowers the raise share is the measurement `utilities.md` §10 records and never a case (D-20, ASM-29). The utility's arithmetic has no entry point of its own — the transform is applied where the transition record is built — so the reward's exact value is asserted at module level rather than here, which is the boundary `e2e-surface.md` §1 draws (D-13, `utilities.md` §4). Nor does it assert that a folder makes a learner **aggressive**: the three folding baselines are asserted as rules — where each folds and where it does not — and whether facing them raises a learner's bet share is the measurement `folders.md` §6 records and never a case (D-21, ASM-31).

And it does not assert the sized action's *verdict*: FAM-20 asserts that the bands are disjoint, that a recorded amount attributes to one descriptor, that the greedy mode decides without a draw and that the pass is bounded — the machinery — and whether a trained learner's census meets the criterion is the pinned measurement of `sizing.md` §7, computed by a script from a run record and never a case (D-29, D-11).
